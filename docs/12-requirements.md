## 12. 요구사항 명세 (SRS) — 확정 (2026-08-14)

> 여기서 SRS = **Software Requirements Specification**. §6의 SRS(Spaced Repetition System)와는 무관한 동음 약어.

§2~§11에 흩어진 요구사항을 검증 가능한 형태로 한곳에 모으고, 설계 단계에서 비어 있던 **보안(§12.4)·백업(NFR-04) 요구를 신규 확정**한다. 구현 중 "이거 하기로 했었나?"는 이 문서로 판정한다.

### 12.1 범위와 우선순위

- **[C]** = 컷오버 필수 (1차 출시: 스페인어 모듈 전체 + 홈·activity·reflection 골격, §6.5)
- **[P]** = 컷오버 이후 (책 §7, CS §8, 영어 확장 §6.2)

### 12.4 보안 요구사항 (SEC) — 신규 확정

위협 모델: **공개 URL(Vercel) + 사용자 1인**. 실질 위협은 ① 낯선 사람의 계정 생성·접근 ② 키 유출 ③ 저장 콘텐츠 XSS 세 가지가 전부다.

| ID | 우선 | 요구 |
|---|---|---|
| SEC-01 | C | **신규 가입 서버 차단** — Supabase Auth 설정에서 "Allow new users to sign up" **off**, 본인 계정은 대시보드에서 수동 생성. 회원가입 UI가 없어도 Auth API로 직접 가입이 가능하므로 UI 부재만으로는 불충분. RLS가 "authenticated 전부 허용"(#33)이라 **이 설정이 사실상 유일한 접근 통제선** |
| SEC-02 | C | RLS 전 테이블 활성 + anon 전부 거부 (§9.2 그대로) |
| SEC-03 | C | 키 관리 — `service_role` 키는 서버 환경변수 전용, 클라이언트 번들·리포 커밋 금지. 브라우저에는 anon key만. `.env*`는 gitignore |
| SEC-04 | C | Storage 버킷 **private**(공개 버킷 금지) + authenticated 정책. 이미지 표시는 signed URL 또는 인증 경유 |
| SEC-05 | P | 마크다운 렌더 시 HTML sanitize(rehype-sanitize 등) — 입력자가 본인뿐이어도 저장 XSS를 습관적으로 차단, 비용 0 |
| SEC-06 | C | HTTPS 전제(Vercel 기본). 커스텀 보안 헤더·CSP 튜닝은 스코프 외 |
| SEC-07 | — | **명시적 비채택**: 레이트리밋·감사 로그·2FA·세션 정책 커스텀 — SEC-01이 성립하면 1인 규모에서 실익 없음 |
| SEC-08 | C | **비밀번호 분실 복구 = 운영 절차** (아래 런북). 앱 내 "비밀번호 찾기" 플로우는 비채택 — 재설정 페이지·이메일 설정이 필요해지는데, 프로젝트 소유자 본인이라 대시보드/admin API로 즉시 재설정 가능하므로 코드 0줄이 이김. 다중 사용자 확장 시에만 앱 내 플로우 추가 |

> SEC-08 보완 (2026-08-15, #50): **기억하고 있을 때의 변경**은 홈 ⚙ → 비밀번호 변경(로그인 세션 필요). 아래 런북은 **잊었을 때의 복구** 전용.

**SEC-08 복구 런북** — 앱 비밀번호를 잊었을 때:

1. Supabase 대시보드에 로그인한다 (앱 비밀번호와 무관한 별도 인증). **이 대시보드 계정이 진짜 최상위 복구 수단**이므로 이쪽 로그인 수단(GitHub 계정 등)을 잃지 않는 것이 중요
2. Authentication → Users에서 유저의 UUID 확인. 대시보드가 비밀번호 직접 변경 UI를 제공하면 그걸로 끝
3. 아니면 admin API 한 줄 (service_role 키는 서버 환경변수에 이미 보유, SEC-03):

```bash
curl -X PUT "https://<project-ref>.supabase.co/auth/v1/admin/users/<user-uuid>" \
  -H "apikey: $SERVICE_ROLE_KEY" -H "Authorization: Bearer $SERVICE_ROLE_KEY" \
  -H "Content-Type: application/json" -d '{"password":"새 비밀번호"}'
```

이메일 발송이 없으므로 SMTP 설정·재설정 페이지가 전혀 필요 없다. 세팅 단계(§12.6)에서 이 절차를 1회 실제로 리허설해 검증한다.

### 12.5 공백 점검 결과 (기능·비기능 완성도 확인)

이번 점검에서 확인된 미비점과 처리:

- **가입 차단 미명시** → SEC-01로 확정 (설계 문서 전체에서 유일한 실제 보안 구멍이었음)
- **백업 주기·절차 미정** → NFR-04로 확정 (§2.2에 "정기 백업" 한 줄뿐이었음)
- **`shared/search` 모듈(§3.2) 미설계** → 전역 검색은 스코프에서 제외하고 목록별 검색(FR-06)으로 한정. 필요해지면 후속 설계
- **reflection entry 수정 정책 미정** → append-only 원칙대로 수정·삭제 UI 없음 확정 (FR-04)
- **모니터링·로깅** → Vercel 기본 로그로 충분, 별도 도구 비채택
- 그 외 기능 요구는 §5~§11에서 전부 확정되어 있음을 확인 — 화면 인벤토리(§11) 기준 누락 없음

### 12.6 수용 기준

컷오버 판정 = §6.5 기능 기준 + 본 문서 **[C] 전 항목** 충족.

특히 SEC-01~04는 **Supabase 프로젝트 생성 직후** 체크리스트로 즉시 적용한다:

1. Auth signup off 확인
2. anon key로 REST 직접 호출 시 전 테이블 거부 확인 (RLS 동작 검증)
3. `service_role` 키가 클라이언트 번들·리포에 없음 확인
4. Storage 버킷 private 확인
5. 비밀번호 재설정 런북(SEC-08) 1회 리허설 — admin API로 실제 변경해 보고 새 비밀번호로 로그인 확인
